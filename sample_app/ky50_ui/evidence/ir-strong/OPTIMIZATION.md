# 强活体优化记录

## 改动与约束

仅修改人脸SDK及相关回归，主应用重新同步静态库并强制重链接。公开`pvaFaceLiveIr`签名、成功判据和既有参数不变。

- CV184X的IR入口仍持有特征锁，保护活体/特征缓冲、配置和生命周期；RGB/IR检测的模型输入、推理、输出解码使用独立检测锁。IR活体阶段允许RGB Pose继续。其他平台沿用原入口互斥。
- IR活体从NV12直接转换裁剪区域，保持奇数ROI原点的UV对应关系、limited-range颜色转换、Reflect101填边及原活体缩放；全UV=128时使用逐值等价的灰度转换。
- 新增锁等待、检测准备、检测模型/解码、IR检测、IR裁剪、活体缩放及模型阶段计时。`liveness_ir`新口径包含直接裁剪；完整调用仍以`BIO_IR_LIVE elapsed_us`比较。
- 每次候选仍执行IR检查，不复用旧true；RGB质量/活体、IR阈值、匹配确认次数及成功冷却均未放宽。绿色框与成功信息仍在所有检查通过后提交。

## 验证

主机ASan/UBSan通过：IR拒绝路径、Pose缓存、特征互斥、活体阶段Pose可继续、参数修改与退出等待在途IR检查。另有176组原始裁剪/缩放用例通过；为限制板端内存，将超大填边用例保留于小尺寸输入，最终168组在ARM板上通过。测试仅用合成数据，没有读取/保存相机图像。

ARM上全部16777216组Y/U/V组合与原标量颜色转换逐字节一致；28组检测画布/通道排列、64组NV12检测输入及168组IR ROI/活体缩放对照通过。日志见[opt-arm-pixels.log](opt-arm-pixels.log)、[opt-sdk-api-tests.log](opt-sdk-api-tests.log)、[opt-preprocess-host.log](opt-preprocess-host.log)。

首轮未限制最大填边尺寸的ARM测试退出137（Killed），大图同时保留多份RGB缓冲，疑似内存压力；内核环形日志未保留明确OOM条目，不作为已确认根因。旧主应用PID750仍存活，后续采集/检测恢复。随后限制测试内存，正常停止媒体应用，再执行完整ARM像素回归并通过；该过程没有强杀或卸载媒体模块。

## 第二轮实拍结果及剩余耗时

原始日志`build/ir-opt/comparison-y.log`，提取明细见[opt-y-timing.json](opt-y-timing.json)。本轮8次人脸成功，另有2次掌静脉成功；不把后台`result=0`以外的失败任务混入成功耗时。成功识别后台任务中位数670.890 ms（647.146～701.437），IR通过调用中位数212.305 ms（197.489～230.669）。与接入版919.044/444.098 ms相比约下降27%/52%；为跨轮现场小样本，非同帧严控基准，不保证每次收益相同。

活跃窗口elapsed 260～295的采集23.97～24.80 fps，检测周期最大254.76 ms；预览帧率维持，但完整响应仍慢。末次成功任务的分解（各自中位数，不能机械相加等同于总中位数）：

| 环节 | 墙钟时间 | 说明 |
| --- | --- | --- |
| RGB特征及认证 | 453.554 ms | 包含原RGB活体，强活体不会替代它 |
| IR检查 | 212.305 ms | 只Y处理后仍需独立检测及活体 |
| 后台完成到业务确认 | 77.500 ms | 3～94 ms，结果在下一次双模态检测完成后消费 |
| 考勤记录保存 | 78.223 ms | 72.600～164.842 ms，识别线程同步SQLite调用 |
| 保存后到上屏估算 | 36.871 ms | 21.880～60.158 ms，含余下业务和显示，并非纯LVGL |
| 末次成功任务开始到成功上屏 | 867.544 ms | 逐条相加后取中位，范围852.407～907.437 ms |

`FACE_CONFIRM uptime_ms - BIO_STAGE uptime_ms`用于结果交接；成功上屏用确认时间加`ACCESS_PRESENT age_ms`。`age_ms`已包含保存记录，不能再将考勤时间重复加进去。这里不含首次画面采集、检测和之前失败尝试。

RGB中最重的是原RGB活体：墙钟234.528 ms、线程CPU55.587 ms，其中缩放/输入图准备172.868 ms、CPU42.555 ms；活体模型调用中位14.287 ms（包含打包、推理、输出及等待，并非纯硬件执行时间）。全幅RGB NV12转换为95.978 ms、CPU23.620 ms。RGB六个已计时阶段CPU合计中位98.028 ms；未归入这些阶段的RGB残余仅1.440～23.065 ms，包括SDK身份匹配及未计时开销，现有日志不能把它精确等同于数据库比对耗时。

IR中，独立检测90.468 ms、CPU21.657 ms；Y裁剪13.288 ms、CPU3.955 ms；单通道缩放/模型输入90.534 ms、CPU23.581 ms；活体模型调用10.972 ms。IR检测和活体阶段CPU合计中位50.345 ms。IR入口特征锁等待约0.005 ms，旧的整段检测锁已非当前主要瓶颈。

板端`/proc/cpuinfo`仅有一个Linux CPU，见`build/ir-opt/scheduling-state.log`。业务线程nice=1、检测线程nice=3，UI/采集等其他线程继续运行。约148 ms的已计时CPU工作被放大到约671 ms墙钟，说明仅看函数耗时会混入大量非CPU执行时间。NV12转换等CPU处理同样出现约4倍墙钟放大，支持调度/资源竞争的判断。内核未提供可用的每线程schedstat，本轮不能将差额全部精确归因于调度；NPU、锁和其他等待也包含其中。没有证据表明单纯NPU算力是当前最大开销。

### 重试是用户仍感到很慢的重要原因

8组成功前共出现10次RGB质量未通过（25）、5次RGB活体未通过（26且没有执行IR）、3次IR检查未通过。3次IR失败中有2次未进入IR活体阶段，bool无法进一步区分检测、几何等原因；不能都描述为活体分数不够。

按每组首次特征任务到成功上屏计算，中位1748.938 ms，范围1317.121～1940.126 ms；不是从首次入画开始，实际感知还可能更长。例：第1组依次是167 ms质量失败、382 ms和399 ms RGB活体失败，最后666 ms成功任务，加交接及显示约1.94秒。失败样本没有模型分数记录，不能仅凭状态断言是光照、姿态、运动还是模型阈值问题。

### 后续优先顺序

1. 优先减少RGB全幅转换和活体三通道前处理，再结合单核调度评估采集/检测/特征线程的CPU分配；不能只继续压缩IR，也不能用提高优先级导致预览卡顿换取表面加速。
2. 分析初始质量/RGB活体失败样本的分数和采样时机，保留现有安全阈值；当前确认1次、成功冷却0秒，反复尝试不是固定冷却造成。
3. 评估让已完成任务及时唤醒业务处理，继续验证最新在场/掌优先/取消条件；现实现`main.c`先完成两种检测，`access_biometrics_frame`之后才取后台结果。
4. 评估将成功后的考勤持久化从显示路径拆开。当前`access.c::face_auth_complete`先执行`store_record_match_kind`再发布成功；`access_store.c`使用SQLite DELETE日志和synchronous=FULL。若异步化需保留记录顺序、失败反馈和退出排空，不能直接关闭可靠写入。

本次现场反馈后只做了上述分析和文档更新，未调整线程优先级、活体阈值、重试规则或存储语义；当前仍运行Y优化版。
