```c
#ifndef PVA_PALM_SECOND_KEYPOINT_ENABLE
#define PVA_PALM_SECOND_KEYPOINT_ENABLE 0
#endif
```

控制 `getFeatPorcess` 的整段“1.5倍大图裁剪、旋转、二次检测并替换框/关键点”。
关闭后原图指针、尺寸和首次检测Pose直接进入后续特征流程；保留首次检测、特征ROI裁剪、
192×192小ROI任意角旋转、质量判断、特征提取与匹配。没有改变显示副本、掌优先、异步取消或离场去重。

CMake同名选项默认OFF；`scripts/build_cv184x.sh` 明确传入 `${PVA_PALM_SECOND_KEYPOINT_ENABLE:-OFF}`，

```sh
PVA_PALM_SECOND_KEYPOINT_ENABLE=ON scripts/build_cv184x.sh
```

默认构建直接执行脚本；主应用随后 `make pva-sync` 和 `make -j8 -W pva/lib/libpva.a package`。
开关仅编译期有效，不加入应用参数页或pvaConf.json。

## 3. 当前剩余延迟与方案

本轮成功样本的墙钟中位值；阶段中位不能直接相加，也不是物理入画到成功的完整时间：

| 阶段 | 掌（10次） | 人脸，仅IR活体（7次） |
| --- | ---: | ---: |
| 后台特征+匹配+所需活体 | 66.462 ms | 373.607 ms |
| 结果完成→业务接收 | 64 ms | 17 ms |
| 同步考勤记录 | 79.345 ms | 82.310 ms |
| 记录完成→UI提交（推算） | 39.085 ms | 36.185 ms |
| 成功任务开始→UI提交 | 243.427 ms | 509.185 ms |

人脸RGB候选部分中位208.717 ms，IR检查156.616 ms（其中IR检测98.728 ms、IR活体部分58.311 ms）。
第一次已记录任务到成功UI的人脸中位1162 ms，中位3次尝试；可能包含出入画面和调整姿态间隔，
不能当作精确的物理入画延迟。采集间隔均值40.924 ms（约24.4 fps），双Pose检测均值99.431 ms。

### 结果交接

`main.c:inference_worker` 先串行执行掌Pose和人脸Pose，再调用 `access_biometrics_frame`，
后者才 `bio_worker_take`。所以任务已完成时仍可能等一轮检测；这不是匹配库本身需要等待。
仅增加信号而仍在同一个正在执行Pose的线程取结果，不能完全解决问题。

建议将业务状态消费从检测循环拆出，检测和认证任务都向**单一业务线程**发布带序号事件，认证完成即唤醒消费。
必须继续校验模态原始检测、掌优先、配置/页面/会话generation、结果1500 ms有效期和离场取消；
不从后台特征线程直接调用access/SQLite/UI。检测状态更新及结果处理有明确顺序，保持每次停留仅一次成功。
这针对掌本轮41～78 ms、其中位64 ms的交接等待；实际节省量要在实现后测量。

### 考勤写入

`access_store.c` 当前是 `journal_mode=DELETE`、`synchronous=FULL`；
正式数据库位于 `/dev/ubi1_0` 的 UBIFS `/mnt/system`，挂载参数包含 **sync**。
因此写盘等待分布在事务内的多个操作，不仅在COMMIT。

| 实际考勤阶段中位 | 掌 | 人脸 |
| --- | ---: | ---: |
| BEGIN | 0.145 ms | 0.123 ms |
| 清理已导出旧记录 | 0.715 ms | 0.722 ms |
| 记录数查询 | 0.102 ms | 0.117 ms |
| INSERT考勤 | 36.710 ms | 39.542 ms |
| UPDATE人员统计 | 13.252 ms | 6.451 ms |
| COMMIT | 24.893 ms | 29.635 ms |

优先方案是验证并采用 **WAL + FULL**，保留每次提交同步语义。
另在同一UBIFS分区独立临时数据库，用相同 `store_record_match_kind` 和表结构、320条合成记录
进行DELETE→WAL→WAL→DELETE对照；每组2次预热+10次测量，各模式20次。
实际PRAGMA读回校验journal模式和synchronous=2。主应用继续运行；没有读取或改写正式人员数据、
没有修改挂载选项，所有自建临时数据库已清理。该实验不包含真实相机特征任务的负载。

| 临时数据库同步事务 | 中位 | 范围 |
| --- | ---: | ---: |
| DELETE + FULL | 59.587 ms | 48.826～72.630 ms |
| WAL + FULL | 27.750 ms | 21.145～39.177 ms |

本实验减少31.837 ms，约53%；不能直接声称真实考勤79～82 ms一定降到28 ms。
还需实现并验证checkpoint安排、退出、容量满/写失败、SQLite在线备份、跨连接一致性及断电恢复。
WAL未checkpoint的数据可能仍在-wal文件，不能以直接复制主数据库文件代替现有SQLite备份API。

可以把考勤放到独立写线程，使用独立连接、不可变事件快照、有界队列及事件唯一ID防重复；
业务确认后先锁住该次停留，待写入回执再统一发布绿框/文字/继电器，保持当前显示及失败提示语义。
这样能避免写库拖慢检测，但若仍等回执，写盘本身依然占总响应时间；应与WAL一起做。
若改为入队立即显示成功和开锁，才可把写盘完全移出成功显示路径，但断电前尚未落盘的事件可能丢失，
且写失败要补发提示。这是另外的业务取舍，本轮未实施。

**本轮只实现默认关闭二次关键点及诊断日志。结果消费线程、WAL和异步写库均为已分析的后续方案，
没有更改正式数据库模式、同步级别或文件系统挂载。**
